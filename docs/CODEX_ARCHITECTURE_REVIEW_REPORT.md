# E23跑起来 V2 架构评审报告

**评审角色：** E23跑起来 V2 项目技术负责人  
**评审日期：** 2026-07-27  
**审计基线：** `codex/e23-phase1-gps-map-fix` / `8054d9547c7eb665b5405218182c638a421e7fdb`  
**审计边界：** 仅审查；未修改代码、数据库、迁移或运行时配置。

## 1. 总体结论

### 是否符合项目初衷

**产品方向正确，但当前实现仍处于“真实多人平台底座 + 本地单人应用”之间，尚未形成可上线的真实班级运动闭环。**

项目的目标、路线数据、Android GPS 与 Supabase 模型都围绕“真实成员 → 真实运动 → 云端累计 → 班级共同推进约 27,000 km 路线”设计；这与 E23 初衷一致，也没有把产品定位成单纯 GPS 工具或单机游戏。

但当前地图的“班级接力图”仍读取本机 `store.classTotalKm`，其实现等于个人本地总里程；云端 `class_stats` 和 `route_progress` 虽有仓库层与订阅封装，尚未进入地图主展示链。若多人开关提前启用，界面会把本机个人里程展示为“全班累计”，构成高风险的假多人呈现。

### 当前阶段判断

**Phase 2.1C 基础完成，Phase 2.1D 是真实多人业务闭环的必要门槛，尚未达到真实班级平台发布条件。**

当前可作为：

- PWA + Android 原生 GPS 的个人真实跑步记录基础；
- Supabase Auth、RLS、活动、统计、路线进度的数据模型基础；
- 后续 50–100 人班级平台的可演进起点。

当前不可作为：

- 已验收的云端班级累计、实时排行榜或真实路线推进系统；
- 可宣称“全班多人已上线”的产品；
- 已完成 iPhone/PWA/Android 统一真实数据体验的正式版本。

## 2. 当前架构评分

| 维度 | 评分 | 结论 |
|---|---:|---|
| 产品方向 | 8/10 | 目标清晰，27,000 km 班级挑战和个人贡献链路正确；必须统一路线计量口径。 |
| 技术架构 | 7/10 | React/Vite/TypeScript/PWA + Capacitor Android + Supabase 是合理的渐进式组合；当前同时保留 Supabase、旧 API/Backend 与 localStorage，运行时事实源不够清晰。 |
| 数据设计 | 6/10 | 表模型、幂等键、轨迹分表、统计表和索引有良好基础；实际写入、统计 Trigger、路线推进尚未以真实活动验收。 |
| 多人能力 | 4/10 | Auth 与 RLS 隔离基础存在，但成员入班、活动写入、云端团队读取、Realtime 和排行榜尚未闭环。 |
| 扩展能力 | 7/10 | 100 人规模的表结构和索引可起步；轨迹保留策略、队列处理器、读模型与运营归档仍需补齐。 |

## 3. 已完成能力确认

### 产品与客户端

- 路线包为 27,171 km，满足 V2 “约 27,000 km”目标；V1 的 21,423 km 已明确为历史基线。
- React 19、Vite 7、TypeScript、PWA 与 Leaflet/OSM 的组合适合先以网页为主入口。
- Android 使用 Capacitor 8 + 原生前台 GPS 服务 + SQLite，适合作为 Android 端增强，而不是另建一套业务后端。
- 本机跑步记录、GPS 质量评估、用户标识隔离和本地活动展示具备基础。

### 云端与安全

- Supabase Auth、`profiles`、`classes`、`class_members`、`run_activities`、轨迹点、个人/班级统计、路线进度、解锁与队列表均已建模。
- `client_id` 对活动提供幂等基础；轨迹点以 `(activity_id, seq)` 去重。
- RLS 默认隔离个人活动；班级统计和路线进度采用服务端 Trigger 聚合，方向正确。
- 后续迁移已收紧 `admin_add_class_member`：要求已审批管理员，并撤销 PUBLIC/anon 执行权限。

### 明确尚未完成

- 新注册用户的入班流程仍调用被 RLS 明确禁止的 `class_members` 直接 INSERT；没有接通受控管理员/邀请审批流程。
- 活动在前端会先落 localStorage，再尝试 Supabase；失败只静默保留，未形成可观测的可靠回补闭环。
- `CloudStatsRepo` 与 `CloudRealtime` 仅封装，地图和排行榜未消费其云端事实数据。
- `sync_queue` 云端表没有消费者；前端另有 localStorage outbox，且面向旧 API，不是 Supabase 队列的完整实现。
- Realtime、PWA 公网部署、双浏览器、iPhone Safari、Android 真机锁屏 GPS 均未完成产品验收。

## 4. 数据链完整性与假多人风险

### 目标数据链

```text
Supabase Auth
  → profiles（审批/班级归属）
  → run_activities（真实、幂等、可审核活动）
  → class_stats（仅 valid 活动的班级总计）
  → route_progress（同一计量口径的路线推进）
  → 地图、排行榜、动态的只读云端展示
```

### 当前实际链路

```text
GPS / 手动输入
  → localStorage / Android SQLite
  → 尝试 Supabase upsert（失败静默）
  → 当前地图继续读取本机 records
```

因此，云端数据链**尚未闭合**。更具体地说：

1. `Auth → profiles`：注册时创建 pending profile，成立；但班级归属无法由普通用户完成，审核后入班没有已接通的前端路径。
2. `profiles → run_activities`：前端具备 upsert 调用，但文档证据显示真实活动 INSERT 曾被 RLS/Trigger 链阻挡，且没有本次基线的真实写入验收。
3. `run_activities → class_stats → route_progress`：Trigger 有结构，但尚无真实业务活动验证；`UPDATE`/`DELETE` 时若活动换班，函数只重算 NEW 班级，旧班级不会回算。
4. `route_progress → 地图展示`：未接通。地图始终使用本机总里程。
5. `Realtime`：存在订阅封装但未在页面注册，更没有双浏览器验收。

### 是否存在假多人风险

**存在，风险等级：高。**

不是伪造同学名单或伪造排行榜数据，而是“展示层将本机个人真实数据误标为班级真实累计”的语义性假多人风险：

- `MapPage` 的 team 视图使用 `store.classTotalKm`；该 getter 当前等于 `store.myTotalKm`。
- 当 `VITE_MULTIPLAYER_ENABLED=true`，原本的“本机贡献”提示会隐藏，但 team 数字仍非云端班级统计。
- `RankPage` 在多人开关开启后没有接入云端 leaderboard，也没有显式的“未接通”状态。

发布前必须保证：团队数字只来自 `class_stats` / `route_progress` 的服务端读模型；读失败时显示“班级数据暂不可用”，不能回退并标记为全班累计。

### 路线计量口径冲突

**✅ 已裁决：E23 V2 正式规则为 1:1（真实跑量 = 班级路线推进），由 Migration 007 纠偏统一。**

- 当前地图、路线包、跑步页和产品文案使用 **1:1 真实公里**。
- `003_team_stats_trigger.sql` 与 `006_route_target_27000.sql` 的 `route_progress.completed_km` 曾以 `total_m / 10000` 计算（即 **1:10**），属历史错误口径。
- **解决**：`supabase/migrations/007_route_progress_ratio_1_to_1.sql` 将 `completed_km = total_m / 1000.0`（1:1），并全量回算现有数据；前端展示本为 1:1，云端与前端现已统一。

这不是展示问题，而是团队核心事实定义不一致。已按 V2 界面和“个人贡献公里 → 团队累计”的目标统一为 **1:1**；云端 Trigger、回填脚本、验收用例和历史数据迁移均已一次性统一（Migration 007 + 恢复脚本同步修正）。

## 5. 最大风险 TOP10

| 优先级 | 风险 | 影响 | 建议 |
|---:|---|---|---|
| 1 | 地图团队视图读取本机总里程 | 形成语义性假多人 | 团队页面只读云端统计；失败显示不可用。 |
| 2 | 1:1 与 1:10 并存 | 路线、贡献和完成率不可信 | **✅ 已解决（Migration 007）**：统一为 1:1（completed_km = total_m/1000.0），Trigger、回算、恢复脚本、文档已同步。 |
| 3 | 成员入班链未打通 | 新同学无法成为真实成员 | 用受控审批/邀请 RPC 接入前端，禁止客户端直接写敏感归属。 |
| 4 | 活动写入/统计尚未真实验收 | 无法证明班级里程真实累计 | 对 A/B 真实活动完成 insert、重试、统计、进度、删改回算验收。 |
| 5 | localStorage 仍承担主展示来源 | 换机、离线、云端冲突时事实不一致 | 明确云端为已登录用户事实源；本地仅缓存/outbox。 |
| 6 | sync_queue 双实现且无消费者 | 离线数据可能长期滞留或丢失 | 统一到一个队列协议，定义 retry/backoff/冲突/死信/用户切换规则。 |
| 7 | Realtime 未接入页面且未验收 | 共享体验只是设计，不是能力 | 订阅班级读模型，双浏览器验证并提供轮询降级。 |
| 8 | Trigger 对跨班 UPDATE 不完整 | 统计可能失真 | 设计为 NEW/OLD 两个 class_id 都重算，并在事务内验证。 |
| 9 | 路线 master 与 DB 读模型脱节 | 只能显示总比例，不能准确解锁城市 | 建立版本化、校验和、节点累计里程的只读 route master。 |
| 10 | PWA/iPhone 与 Android真机未验收 | 平台承诺不能成立 | PWA 作为主路径验收；原生能力按平台降级并记录。 |

## 6. 是否需要重构

### 必须保持

- React + TypeScript + Vite + PWA 为共享 UI 主体。
- Capacitor + Android 原生 GPS 作为 Android 的增强采集层。
- Supabase Auth + PostgreSQL + RLS + Trigger 作为多人事实源方向。
- 活动 `client_id` 幂等、轨迹点分表、`valid/pending/rejected` 状态模型。
- 约 27,000 km 的 V2 路线目标；不得回退为 V1 的 21,423 km。

### 建议优化（不需要推倒重来）

- 将 `CloudRepository` 从通用无类型 CRUD 收敛为面向活动、统计、路线的强类型仓库。
- 将本地 SQLite、localStorage、Supabase、旧 API 后端的职责写成单一数据源契约，避免同一活动通过两条协议上传。
- 对轨迹点增加批量写入大小、保留周期、归档和导出策略；50–100 人规模的活动摘要不是瓶颈，轨迹点才是。
- 地图与排行榜使用云端读模型，不从客户端扫描活动表汇总。

### 必须重构

**不需要整体技术栈重构；需要进行一次小而关键的“数据事实源与团队读模型重构”。**

范围应限定为：

1. 确定唯一的活动上传和离线回补协议；
2. 让个人/团队/路线页面只消费明确的云端读模型；
3. 统一 1:1 或 1:10 的唯一计量口径；
4. 修正成员审批入班、活动写入与 Trigger 读写闭环；
5. 把 Realtime 作为云端读模型的增量刷新，不作为唯一正确性机制。

不建议重写 React、替换 Supabase、重建 Android 工程或另建原生 iOS 代码库。

## 7. Phase 2.1D 建议路线

1. **先完成“事实定义冻结”**：确认路线计量口径、有效活动规则、审批规则、异常数据处理规则；把 27,000 km 与路线 master 版本绑定。
2. **完成 Supabase 写入最小闭环**：管理员审批/入班 RPC、真实活动 INSERT/upsert、`client_id` 重复写入、RLS A/B 隔离。
3. **验证服务端聚合**：以两位用户的真实测试活动验证 `class_stats`、`route_progress`、UPDATE/DELETE/重试的幂等与回算。
4. **替换团队展示数据源**：地图、排行榜、动态改为云端只读模型；云端不可用时明确降级，不显示个人数据冒充团队数据。
5. **统一离线同步**：完成队列状态机、网络恢复、登录切换、失败可见性、重复上传与冲突策略；不再维护两套未贯通队列。
6. **Realtime 双浏览器验收**：验证两个真实账号在同一班级中的活动、班级总里程、路线进度更新；加入轮询/手动刷新降级。
7. **平台验收与发布准备**：公网 PWA、iPhone Safari、Android 真机锁屏 GPS；之后再决定是否需要独立 iOS 容器。

## 8. 最终技术负责人建议

E23跑起来 V2 已具备成为真实多人班级运动平台的**架构基础**，但尚未具备真实多人平台的**交付资格**。下一阶段应坚持“先数据真实性、后体验增强”的顺序：

- 先让每一公里都可追溯到真实用户、真实活动、明确状态和唯一云端记录；
- 再让每一公里可靠地汇总到班级、路线与排行榜；
- 最后使用 Realtime、地图动效、第三方平台导入与原生能力提升参与体验。

发布门槛建议为：两名真实账号、两台设备、一次离线后回补、一次重复同步、一次活动更正/删除、一次双端实时刷新，均能让云端 `run_activities → class_stats → route_progress → 地图` 保持同一数值。未满足前，应继续将多人状态标记为“联调中”，不得对班级成员宣称全班累计已正式上线。
