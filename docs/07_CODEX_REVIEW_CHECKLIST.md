# E23跑起来 · Codex 架构评审清单

## 评审目标

请在评审过程中回答以下关键问题，并在评审完成后记录结论。

## 一、架构是否符合E23初衷

- [ ] APP的核心链路是否清晰？（个人运动 → 贡献公里 → 班级推进路线）
- [ ] 是否避免了“假多人”（伪造排行榜、伪造班级进度）？
- [ ] 路线目标是否冻结为~27,000km？
- [ ] 同学使用路径是否直观？（登录→跑步→保存→看到班级进度）

## 二、是否存在单机残留

- [ ] SQLite数据是否能正确同步到云端？
- [ ] localStorage是否已降级为纯缓存（非主数据源）？
- [ ] 离线时能否正常使用？恢复网络后能否自动同步？
- [ ] 换手机后数据能否从云端恢复？

## 三、是否存在假多人

- [ ] 多人数据是否只来自真实用户的真实活动？
- [ ] 云端统计是否只基于valid状态的run_activities？
- [ ] 是否有任何伪造的排行榜数据？
- [ ] 前端统计闸门是否正常工作？（MULTIPLAYER_ENABLED）

## 四、数据库设计是否可长期运行

- [ ] 表结构是否支持100用户×每周10活动×2年？
- [ ] client_id幂等性是否保障？
- [ ] RLS策略是否正确？
- [ ] 索引是否合理？（user_id, client_id, class_id, created_at）
- [ ] Trigger逻辑是否正确处理UPDATE/DELETE？
- [ ] 数据清理和归档策略？

## 五、Android/iOS/PWA是否统一架构

- [ ] PWA作为主入口是否可行？
- [ ] Android原生GPS是否作为增强而非必要？
- [ ] iOS上PWA的定位能力是否足够？
- [ ] 是否需要独立的iOS应用？
- [ ] Capacitor抽象层是否充分？

## 六、是否支持未来100人规模

- [ ] Supabase免费版配额（500MB DB, 5GB带宽）是否够用？
- [ ] 轨迹点存储策略？（批量写入+压缩）
- [ ] 同步队列的吞吐量设计？
- [ ] Realtime频道数量限制？

## 七、是否需要重构

- [ ] 当前架构的最大问题是什么？
- [ ] 哪个模块的技术债务最严重？
- [ ] 需要多大的重构工作量？
- [ ] 建议立即重构还是后续优化？

## 八、下一阶段优先级

Codex建议的下一步优先顺序：

1. [ ] Supabase RLS/Trigger修正 → 使云端写入畅通
2. [ ] PWA公网部署 → 真实多人可用
3. [ ] Android GPS真机验收 → 核心功能闭环
4. [ ] sync_queue完整实现 → 离线→云端闭环
5. [ ] Realtime双浏览器验证 → 实时体验
